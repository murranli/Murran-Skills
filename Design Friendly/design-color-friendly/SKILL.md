# 设计稿色彩友好化

## 确定任务和规范来源

使用用户指定的稿件或明确选区。区分只盘点或提出建议、保留原值的变量化、按规范校准。用户明确要求修复用色或沿用已确认的校准流程时，可以按用途改为规范值。若任务也包含清理，先处理已验证的冗余项。仅变量化时，记录发现的冗余项，由用户确定是否清理。需要对照且用户未指定位置时，可在原稿附近建立可编辑副本。

优先读取本轮指定的色彩 JSON，其次使用当前项目明确配置的规范。换档时重读新文件的来源、字段说明、规则、记录和未决项，重新核实当前任务涉及的匹配和本地变量。替换文件只确定本次使用的规范来源，稿件写入以当前任务为准。规范缺失时仍可盘点颜色和核查冗余，依赖规范的判断标为待核实。

兼容的 JSON 以 `source` 标识来源，以 `records` 提供条目，以 `rules` 说明使用条件，以 `unresolved` 记录未决项。色彩条目通常包含 `id`、`label`、`hex`、`alpha_percent`、`usage`、`refs`，按需读取状态、模式和例外。替换文件使用其他字段名时，按字段说明映射相同含义。`alpha_percent` 用 0–100，`100` 表示完全不透明，缺失或 `null` 表示待核实。`refs` 用来回查出处。规范变量原名取已核实的 `variable_name`，或字段说明明确标为填充面板名称的 `id`。示意配色和未确认的数据仅供核对。

## 判断颜色是否生效

读取实际填充、描边和文本区间，核对叠放、可见性、混合模式以及填充与图层各自的不透明度。面板里已启用的填充也可能被完全遮盖。清理疑似冗余项时，在副本上临时关闭并比较同范围、同状态、同背景的渲染。确认相关模式、状态和变体均无呈现变化后再移除。证据只覆盖当前状态且该填充可能参与其他状态时，保留并注明待核实。确认变量在整个文件中没有引用且清理范围包含变量时，可移除该无用的本地变量。

只有实际生效的颜色进入规范匹配和命名。实例里当前隐藏的图标或变体内容可能在其他状态使用，按组件行为判断。

## 按用途匹配并应用

先按颜色承担的作用、作用对象和使用条件找规范项，再核对色值、不透明度、模式和状态。用途相同且对应项明确时，即使原值不同也可以作为校准目标。多个规范项同值时按实际用途选。用途不清楚、规范有冲突或有多个合理候选时保留现状，记录位置和需要确认的依据。

- **仅变量化**时，保留现有颜色和呈现。用途和实际值都匹配的颜色可直接绑定。用途已被覆盖但值不同的条目保留当前填充并标为待校准。若用户要求当前色也纳入变量管理，则按原值建立或复用临时变量，并记录拟校准的规范项。
- **校准**时，将用途明确且规范已覆盖的颜色改为规范值。规范尚未覆盖或有明确业务理由保留的用色，按原值维护。记录业务例外的用途和原因。
- **绑定**时，先查现有变量。用途、色值、不透明度、模式及适用属性相符时复用。有可用且已确认的公共库资源时使用实际变量引用。需要在独立文件维护时，按当前项目命名约定创建本地变量。使用本次约定时，已采用规范值的本地变量用 `indep.<规范原名>`，保留原名中的大小写、斜杠和空格。规范仅有本地检索键时，可用该键标明来源并注明其性质。需要独立维护的未覆盖用色或业务例外用 `Unm.<简洁语义名>`。按用途和实际颜色共同判断能否合并。

保留各自的填充与图层不透明度语义，避免绑定后重复计算透明度。按文字区间处理混合用色。用设计工具支持的局部覆盖保留组件关系。同名变量若值或用途冲突，优先在本次专用集合内创建可区分的变量并记录差异。没有合适的独立变量位置时，保留现有画笔并报告冲突。

## 验收和迭代

核对目标颜色、绑定、适用模式和实际渲染。清理和等值绑定应保持可见呈现一致。校准允许指定颜色改变，同时核对其他填充、富文本格式、组件关系和布局。报告实际改动、变量复用或新增，以及影响交付的未决项。

需要参照已验证的判断案例，或用户要求沉淀试用经验时，读取 [references/trials.md](references/trials.md)。规范更新通过更换 JSON 生效。只有新案例暴露可复现的判断缺口时，才提炼并修订通用条款。
