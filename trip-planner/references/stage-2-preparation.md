# 阶段 2：出行准备

本阶段把已知旅行条件转化为一份轻量、目的地相关、可以逐项勾选的准备清单。重点是帮助用户实际完成准备，不是再次比较旅行方案，也不是生成每天的详细行程。

开始前读取 [accuracy-discipline.md](accuracy-discipline.md)；需要查询政策、申报入口、装备环境或当前运营要求时读取 [research-playbook.md](research-playbook.md)。

## 进入条件

开始前至少知道：

- 目的地；
- 出行日期或明确季节；
- 主要活动类型。

用户已经提供的交通、住宿、预订和个人偏好应直接复用。尚未确定的交通或住宿不阻塞基础清单，但依赖准确班次、地址或预订条款的事项只能写成待补任务。

只有某项准备要求确实依赖护照签发国家、转机地、驾照类型、健康情况或其他条件时，才补问相应信息。不要为了填满模板收集护照号、订单号等不必要的敏感数据。

## 工作方法

### 1. 整理已确认的旅行条件

从对话和用户材料中提取：目的地、日期、主要活动、交通、住宿、行李条件、同行特征及已经完成的准备事项。

- 用户已预订的航班、车次和住宿是清单的输入，不在本阶段重新比选。
- 如果用户资料之间明显冲突，先指出冲突并询问，不擅自选择一个版本。
- 没有用户明确反馈时，所有新生成任务保持未勾选；不要根据“应该已经完成”推断状态。

### 2. 识别本次旅行特有的准备要求

围绕以下问题判断需要哪些栏目和条目：

- 是否跨境，是否涉及签证、免签条件、入境卡、海关或转机规则；
- 是否有预订确认、免费取消、值机、行李或入住时限；
- 当地通信、支付、插头、电压、地图和交通工具是否有特殊要求；
- 出行季节、实际天气和主要活动需要哪些衣物与装备；
- 徒步、自驾、海上活动、高海拔等是否需要额外安全准备；
- 是否需要保险、处方药、常用药或重要资料备份。

只保留与当前目的地、季节、活动和用户情况有关的任务。通用旅行清单可以作为漏项检查，但不能未经筛选整份复制。

### 3. 核查高影响任务

- 入境、申报、驾照、保险强制要求和公共安全信息优先使用当前官方来源，并记录查询日期。
- 申报开放窗口、免费取消、线上值机等时限必须区分“最早可操作”“建议完成”和“最晚截止”，不能自行创造一个没有依据的日期。
- 如果确切日期已知，将相对期限换算为明确年月日；只能给相对时间时，写成 `T-7`、`T-1` 等，并注明待日期确定后换算。
- 官方规则无法覆盖用户条件时，把“向责任机构确认”写成行动项，而不是替用户下结论。

### 4. 生成并审计清单

清单以类别为主，不额外生成责任人表、总体完成度或阻断事项摘要。时间要求直接写在对应任务旁边。

输出前去重，检查每个条目是否能够被明确执行或确认。诸如“安全”“注意天气”之类不可勾选的口号，应改写成具体动作。

## 条目写法

默认格式：

```markdown
- [ ] <要完成或携带的事项>（<必要条件或简短说明>）⏳ <明确日期或相对时间>
```

规则：

- 一个复选框对应一个可以明确判断完成与否的事项。
- 同一个操作需要准备多项材料时，使用缩进子清单，不把所有材料塞进一行。
- 条件性事项直接写明“若转机……”“若托运行李……”“若计划自驾……”；不适用的项目不要保留。
- 可选物品只有确实能改善本次体验时才加入，并用“可选”说明，避免与必需事项权重相同。
- 名词式物品可以保持简洁，例如“徒步鞋”；需要规格或数量时只补充影响选择的说明。
- 截止日期放在行动项本身，不另建时间轴或总进度面板。
- 官方链接放在需要执行的任务文字上，避免文末出现无法对应行动的链接列表。

## 分项规则

### 证件、保险与资料备份

- 根据目的地和用户条件核对需要携带的旅行证件及有效要求；不要把“通常适用”写成用户一定符合。
- 资料备份说明需要保存哪些文件、建议语言版本及离线可访问方式，不要求在清单中记录证件号码。
- 保险只列是否需要购买、保障场景和保单存档等准备动作；不做未经请求的具体产品推销。

### 入境、出境与转机申报

- 使用官方入口，写明适用人群、开放窗口、截止时间及查询日期。
- 将填写所需材料作为子清单，例如证件照片、出入境班次、住宿地址和当地联系电话。
- 用户已确认的班次和住宿信息可以直接填入私人清单，并标记为用户提供；不要再次降级为普通候选。
- 缺少必要地址或班次时保留清晰占位任务，例如“订房后补充酒店英文地址”，不要编造内容。

### 预订复核

按实际行程选择需要检查的事项，例如：

- 乘客姓名与证件拼写；
- 航站楼、机场或车站、当地起降时间和是否跨日；
- 行李额度、值机方式和必要凭证；
- 住宿地址、入住/退房、押金、免费取消或付款日期；
- 已预约活动的集合地点、到场时间和取消规则。

这里负责核对用户已有预订，不重新提供机票或住宿候选方案。

### 衣物与活动装备

- 根据天数、季节气候、临近天气、活动强度、行李限制和淋湿/更换需求生成清单。
- 距离出行较远时依据季节风险准备，并加入临近出发时查看天气的任务；进入可靠预报窗口后再调整防雨、防晒、保暖等项目。
- 徒步装备关注鞋履适配、防滑、防雨、防晒、防磨、补水、照明、离线导航和简单急救等真实风险；不要把专业装备无差别加给普通城市旅行。
- 新鞋、新设备或关键装备需要提前试用时，将“试穿/充电/测试”写成独立行动项。

### 洗护、药品与健康

- 根据住宿是否提供用品和活动环境筛选洗护物品，不默认重复携带。
- 药品部分以个人处方药、日常常用药、过敏信息和简单急救准备为主，不提供诊断或替代医疗建议。
- 涉及受管制药物、疫苗或健康申报时，使用当前官方或专业医疗来源，并提醒用户按个人情况咨询。

### 电子设备、通信与电力

- 核对当地插头类型、电压、漫游或流量方案、充电需求和设备防水/保护。
- 区分“转换插头”和“变压器”，根据用户设备输入规格决定是否需要后者。
- 将下载离线地图、保存订单、开通漫游、测试充电设备等写成动作，而不只罗列设备名称。

### 支付、交通卡与现金

- 根据目的地实际接受方式准备银行卡、移动支付、交通卡和少量备用现金。
- 写清交通卡是提前开通、到达后购买还是现场充值；不确定时提供核实入口。
- 不在清单中保存完整卡号、验证码或其他支付凭据。

### App、地图与离线信息

- 只推荐在目的地真正有用的地图、翻译、交通、天气或路线工具。
- 除安装外，根据需要加入登录、下载离线区域、收藏住宿与路线起终点、保存紧急联系方式等具体动作。
- 多个 App 功能重复时给主选和备选，不堆积长列表。

### 出发前最后检查

按旅行情况加入少量临近出发才有意义的任务，例如天气与预警、航班状态、路线开放、证件随身、充电、值机和必要资料离线可用。不要把详细行程内容复制到这里。

## 默认交付结构

输出为可继续编辑的 Markdown。根据旅行类型删减空栏目；没有相关任务的栏目不输出。

```markdown
---
所属国家/地区:
目的地:
出发时间:
回程时间:
出行主题:
tags:
  - 旅行
---

# 证明资料、通信与保险
- [ ] <行动项>

# 入境/出境与转机申报
- [ ] <申报任务及官方链接> ⏳ <日期>
  - [ ] <所需材料>
  - [ ] <用户已确认的班次或住宿填写信息>

# 预订复核
- [ ] <机票、住宿、行李或预约核对项> ⏳ <日期，如有>

# 衣物与活动装备
- [ ] <与季节和活动相关的物品或测试任务>

# 洗护、药品与健康
- [ ] <相关事项>

# 电子设备
- [ ] <相关事项>

# 支付与当地交通
- [ ] <相关事项>

# App 与离线信息
- [ ] <相关事项>

# 其他
- [ ] <少量无法归入以上类别但确有必要的事项>

---
*准备信息核查日期：<日期>。政策、天气与运营状态等高时效事项请按条目要求再次确认。*
```

栏目顺序可以根据紧迫性调整，但不要改成按负责人、完成度或阻断等级组织的项目管理表。

## 待办状态与更新

- 初次生成的任务默认未完成。
- 只有用户明确报告某项已经完成时，才更新对应复选框。
- 用户后续补充机票、住宿或活动预订时，可以更新相关材料子项和截止日期，不要求重写整份清单。
- 若用户要求同步阶段 1 顶部待办，只更新用户确认的实际进展；阶段 1 正文候选方案保持不变。

## 私人与分享版本

- 私人清单可保留完成申报、入住和紧急联系所需的地址、电话及班次信息。
- 发给同行人的版本只保留共同准备所需信息，不暴露不必要的个人证件和支付信息。
- 进入公开 Skill 案例前，将具体电话、私人联系方式、订单号和其他可识别信息替换为说明性变量。

## 交付前质量门槛

- 每项任务与当前目的地、季节、活动或已确认预订有关。
- 高影响政策和申报事项来自当前官方来源，并写明条件与截止时间。
- 截止日期没有把开放日、建议日和最后期限混为一谈。
- 用户已确认信息、待补信息和条件性任务清楚区分。
- 清单条目能够被勾选，没有抽象口号、大量重复或无关通用物品。
- 没有自动勾选用户未报告完成的事项。
- 没有加入负责人、总体完成度或阻断事项摘要。
- 没有重新比较交通住宿，也没有越界生成阶段 3 的详细行程。
- 分享或案例版本没有泄露不必要的敏感信息。
