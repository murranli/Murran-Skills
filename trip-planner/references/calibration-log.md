# 校准日志 Calibration Log

本日志只保存已经获得用户授权、会稳定改变未来行为的高价值规则。先按 [post-trip-calibration.md](post-trip-calibration.md) 区分通用规则、个人偏好、目的地案例和待验证假设；案例过程放入 `references/cases/`，不要把每次旅行的细节都堆进本文件。

未经明确授权，不自动写入本日志。运行普通规划任务时不必默认加载全部案例；只有当前问题命中某条校准规则或需要验证相似案例时再读取相应文件。

写入格式：
```
## YYYY-MM-DD · <一句话标题>
- **现象**：发生了什么（用户怎么发现的）
- **根因**：为什么会这样
- **规则**：以后怎么做（可执行、可检查）
- **适用边界**：何时不应套用（必要时）
```

## 2026-09-02 · 三种旅行交付必须独立路由
- **现象**：同一次济州岛实践先后需要可分享的调研文档、轻量准备清单和固定交通住宿下的详细执行计划；三者的输入成熟度、内容粒度和使用时间不同。
- **根因**：旧版把意图确认、调研、验证和输出当成一条流水线，容易把调研候选、准备任务和详细日程混进同一份文档。
- **规则**：将出行调研、出行准备和详细行程设为三个可独立进入、每轮单独确认的交付阶段；完成一个阶段不自动生成下一阶段。行后校准是旁路，不计作新的出行阶段。
- **适用边界**：用户明确要求合并交付时可以组合，但仍应保持信息状态和栏目边界。

## 2026-09-02 · 官方时长不能直接等于团队总经过时间
- **现象**：济州偶来7号线官方标称3–4小时，4人混合体力团队实际约08:00至15:00；6号线实际行走时长却与计划较接近，主要偏差来自晚起。
- **根因**：旧模型混合了官方移动参考、路线特征、最慢成员速度、休息拍照、购物停留和出发延误，并可能用一次实测给所有路线套统一倍率。
- **规则**：分别记录基础时长、团队移动估值、非移动缓冲、机会缓冲和团队总经过时间；同时给目标出发与最晚安全出发。不同路线单独估算，行后尽量分别记录出发延误与路线耗时。
- **适用边界**：没有实际分段记录时给范围，不伪造移动/停留时间拆分。详见 [济州岛案例](cases/jeju-2026.md)。

## 2026-09-02 · 混合体力团队需要可执行的分流协议
- **现象**：连续徒步第二天，一名成员因睡眠不足在6号线途中退出并独自返回等待地点，其他成员继续完成路线。
- **根因**：晨间状态检查只能决定“走不走”，不足以处理途中个人退出后的导航、交通、报平安和重新汇合。
- **规则**：高强度日前检查睡眠、进食、疼痛和异常疲劳；允许分流时，预先写明道路可达退出点、返回/等待地点、交通方式、通信节点和汇合方案。主计划按最慢但状态合格的成员组织。
- **适用边界**：不适合独自行动的成员应由同伴陪同，安全要求优先于完成全程。

## 2026-09-02 · 行程要同时保护硬边界与偶遇空间
- **现象**：购物、手工艺和海边用餐等临时体验显著提升满意度，但返程日也因购物延后到达机场，并遇到长安检队伍与托运波折。
- **根因**：长表格中的最晚离开时间不够醒目；完全压缩自由时间又会损害旅行体验。
- **规则**：每日前置执行卡，突出目标出发、最晚安全出发、硬截止、切换条件和不可牺牲事项；硬截止之前可设置可取消的机会缓冲，超时先取消机会项而不是侵占返程或安全缓冲。
- **适用边界**：最终顺利完成返程不能反向证明较短机场缓冲安全。

## 2026-09-02 · 行后花费必须先声明口径
- **现象**：济州岛花费摘要可计算类别合计与比例，但没有声明币种、单人/全团，也没有把小交通对应到具体行程段。
- **根因**：类别汇总适合个人记录，却不足以校准预算和逐段交通估价。
- **规则**：行后校准先检查币种、单人/全团、覆盖范围、计划/实际和行程段；缺失时只说明数据缺口，不判断超支或验证某段费用。若只保留类别汇总，至少在元数据中声明币种和口径。
- **适用边界**：口径一致时仍可计算类别占比，但不能据此推导未记录的分项价格。

## 2026-07-23 · 候选航班号被伪装成“已核实”，实际官网不存在
- **现象**：子 agent 报告称"航班号经 Flightradar24 逐一核实真实存在"，输出了 9C7205 等。用户去春秋航空官网查证，发现 9C7205 根本不存在。
- **根因**：① Flightradar24 / flightsfrom 等聚合站会显示历史班次、包机、codeshare、季节性航班，"雷达上飞过"≠"当前航季官网在售"，数据源本身不可交易级。② 更严重的是措辞：把参考推测包装成"已核实"，而用户是会亲自去官网验证的人，假确定信息浪费其核实成本、消耗信任。
- **规则**：对尚未由用户预订的航班、车次、房源、实时价或库存，只能写带查询时间的候选或给官方核实入口；聚合站不能证明指定日期当前在售。用户明确提供的已购信息作为“用户已确认”固定输入保留，但运行状态仍在临行时复核。查不到就说查不到，见 [accuracy-discipline.md](accuracy-discipline.md)。

## 2026-07-23 · 具体房源名检索命中率低，不要硬凑
- **现象**：小红书笔记里的民宿名多是博主个人叫法或已下架/改名，在 Airbnb/Agoda 里搜无结果或评分对不上。用户觉得逐个验证太麻烦，选择"行程定后再挑"。
- **根因**：UGC 里的住宿名不是平台标准名，验证成本高、ROI 低；且行程/人数未定时，选具体房源为时过早。
- **规则**：住宿在**人数/行程未定阶段**，民宿/酒店可合并为"人均¥X 档位 + 平台与选址建议 + 行程定后再挑"，不硬凑具体房源名。青旅等相对标准、紧俏需早订的可保留具体名。给"怎么自己搜"（平台+关键词）比给一个存疑的名字更有用。

## 2026-07-23 · 输出格式以用户迭代版为准
- **现象**：先给了 HTML，用户接受视觉但把内容重排成更精炼的 Markdown（合并民宿块、航班加"价格以9月参考"、行程用时段表+emoji）。
- **根因**：用户（信息可视化设计师）会亲自精修排版；Markdown 比 HTML 更易迭代、粘回 Notion/飞书。
- **规则**：**默认输出 Markdown 可预览文档**，按当前阶段读取 `stage-1-research.md`、`stage-2-preparation.md` 或 `stage-3-itinerary.md`。用户明确要其他格式时再转换。把文档当“可编辑、可继续执行的交付物”，而非不可修改的成品。
