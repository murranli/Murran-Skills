# 校准日志 Calibration Log

本 skill "越用越准"的机制。**每次规划结束、拿到用户反馈后，把可复用的教训追加到这里**（最新在上）。开工前必读本文件——这些是凌驾于流程之上的硬约束。

写入格式：
```
## YYYY-MM-DD · <一句话标题>
- **现象**：发生了什么（用户怎么发现的）
- **根因**：为什么会这样
- **规则**：以后怎么做（可执行、可检查）
```

## 2026-07-23 · 航班号被伪装成"已核实"，实际官网不存在
- **现象**：子 agent 报告称"航班号经 Flightradar24 逐一核实真实存在"，输出了 9C7205 等。用户去春秋航空官网查证，发现 9C7205 根本不存在。
- **根因**：① Flightradar24 / flightsfrom 等聚合站会显示历史班次、包机、codeshare、季节性航班，"雷达上飞过"≠"当前航季官网在售"，数据源本身不可交易级。② 更严重的是措辞：把参考推测包装成"已核实"，而用户是会亲自去官网验证的人，假确定信息浪费其核实成本、消耗信任。
- **规则**：**交易级信息（航班号、车次、具体房源、实时价）永不宣称"已核实"。** 一律标"⚠ 须官网按日期核实"或只给查证入口。子 agent 的"已核实"措辞一律降级。查不到就说查不到。见 `accuracy-discipline.md`。

## 2026-07-23 · 具体房源名检索命中率低，不要硬凑
- **现象**：小红书笔记里的民宿名多是博主个人叫法或已下架/改名，在 Airbnb/Agoda 里搜无结果或评分对不上。用户觉得逐个验证太麻烦，选择"行程定后再挑"。
- **根因**：UGC 里的住宿名不是平台标准名，验证成本高、ROI 低；且行程/人数未定时，选具体房源为时过早。
- **规则**：住宿在**人数/行程未定阶段**，民宿/酒店可合并为"人均¥X 档位 + 平台与选址建议 + 行程定后再挑"，不硬凑具体房源名。青旅等相对标准、紧俏需早订的可保留具体名。给"怎么自己搜"（平台+关键词）比给一个存疑的名字更有用。

## 2026-07-23 · 输出格式以用户迭代版为准
- **现象**：先给了 HTML，用户接受视觉但把内容重排成更精炼的 Markdown（合并民宿块、航班加"价格以9月参考"、行程用时段表+emoji）。
- **根因**：用户（信息可视化设计师）会亲自精修排版；Markdown 比 HTML 更易迭代、粘回 Notion/飞书。
- **规则**：**默认输出 Markdown 可预览文档**，结构见 `output-template.md`（已吸收该迭代版）。用户明确要 HTML 再出 HTML。把文档当"可编辑草稿"交付，而非"成品"。
