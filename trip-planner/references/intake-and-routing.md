# 阶段识别与任务确认

本文件用于判断用户当前需要出行调研、出行准备还是详细行程，并在正式执行前形成一份足够简短、没有重复提问的任务确认。

阶段由**用户本轮目的优先决定**，输入成熟度用于判断是否具备执行条件。用户已经订好机票，并不代表每次请求都必须进入阶段 3；如果他想比较目的地体验或向朋友解释方案，仍可能是在阶段 1。

## 1. 先读取已有上下文

在提问前，从当前对话、用户提供的笔记、订单摘要或其他明确材料中提取已知信息。为了识别阶段和输入缺口，可以只读审阅用户放入范围的材料；在用户确认前，不开始新的外部调研，不扩写正式交付，也不修改原文件。

只复用用户明确提供或允许使用的信息。记忆中的偏好若会影响方案，应在确认摘要中显式呈现，不能作为隐藏前提；未经授权不写入长期记忆。

将相对日期转换为明确日期并向用户展示，例如把“这个周末”解释为具体年月日。交通时间默认按起降地当地时间理解，但需要在确认摘要中写清跨日与时区假设。

## 2. 判断用户本轮目的

| 判断问题 | 若答案为“是” | 路由 |
|---|---|---|
| 用户是否主要在判断这趟旅行是否值得、何时去、怎么去、住哪里或大约多少钱？ | 需要候选方案与取舍 | **阶段 1 · 出行调研** |
| 用户是否主要在核对证件、申报、预订、装备或出发前要完成的事项？ | 需要行动清单 | **阶段 2 · 出行准备** |
| 用户是否主要希望在已确定的交通住宿内，安排每天每个时段和天气备选？ | 需要可执行日程 | **阶段 3 · 详细行程** |
| 用户是否已经结束旅行，希望用实际行程、花费或复盘改进规划方法？ | 需要比较计划与实际并提炼经验 | **行后校准（旁路）** |

关键词只能提供线索，不能单独决定阶段。“攻略”可能是调研，也可能是详细行程；“已经订好”只说明某些输入已确定，不代表用户要求重新规划所有内容。

## 3. 判断输入是否足够

### 阶段 1 · 出行调研

最低输入：

- 出发地；
- 目的地；
- 大致时间窗口和天数；
- 最重要的旅行体验。

准确日期、人数、预算和住宿偏好可以未知。只有缺失项会改变交通骨架、季节可行性或核心体验时才补问；否则在确认摘要中写成假设、范围或待决定项。

### 阶段 2 · 出行准备

最低输入：

- 目的地；
- 出行日期或明确季节；
- 主要活动类型。

交通和住宿信息若已确定，应作为准备材料复用；尚未确定时不阻塞生成基础清单，但与预订、地址或准确截止日期有关的项目只能留作待补或后续更新。

只有具体任务涉及入境、转机、驾车、健康或其他条件性规则时，才询问会改变要求的身份或行程信息。不要为了“完整画像”收集无关或敏感信息。

### 阶段 3 · 详细行程

生成可执行日程前必须明确：

- 准确出行日期；
- 抵达和离开的地点与当地时间，或足以确定它们的航班/车次信息；
- 住宿位置及影响安排的入住/退房条件；
- 已有固定预约、必须保留的活动和其他硬约束。

徒步、自驾、亲子、老人同行或无障碍等情形下，再补问会影响强度、安全和转场的条件。徒步路线选择会因风格偏好改变时，补问铺装/野趣、爬升、暴露感、自然景观和撤退便利度；混合体力团队还需确认是否允许分流及基本汇合方式。不存在固定预约或特殊限制时，允许用户明确回答“没有”，不要求凭空补齐。

若阶段 3 缺少关键输入，不能用常见航班时间、假设住宿区域或虚构预约补齐。可以整理缺口或提供非执行性的结构框架，但必须明确它还不是详细计划。

### 行后校准（旁路）

最低输入是至少一份原计划，以及能够说明真实执行情况的复盘、实际时间记录或花费摘要。资料不完整时仍可分析，但必须区分已观察事实和推断；缺少币种、单人/全团或行程段等花费口径时，不得自行补齐。

## 4. 区分阻塞信息与可声明假设

### 必须先问的阻塞信息

缺失后会导致以下任一情况的信息属于阻塞项：

- 选择了错误的旅行阶段或交付物；
- 改变入境资格、安全边界或重要政策结论；
- 无法判断出发地、目的地、旅行日期或抵离边界；
- 可能覆盖用户已经预订或明确决定的事项；
- 阶段 3 无法形成完整、可执行的时间框架。

一次只问最少数量的阻塞问题，优先合并为 1–3 个简短问题。已有答案不再询问。

### 可以声明后继续的假设

以下内容通常可以先给合理默认，并在确认摘要中公开：

- 未明确的预算档位，以范围或不同取向比较；
- 普通成人步行能力，但行程涉及高强度户外时除外；
- 没有特别饮食或无障碍要求；
- 阶段 1 的具体住宿和活动尚未决定；
- 用户未指定格式时使用可继续编辑的 Markdown。

假设只是为了推进调研，不得被写成用户偏好或长期事实。用户纠正后立即更新本轮约束。

## 5. 拆分混合需求

用户在同一请求中要求调研、准备清单和详细行程时：

1. 把请求拆成三个可独立确认和交付的任务；
2. 说明它们之间的依赖关系；
3. 推荐先执行能够为后续提供输入的阶段；
4. 等用户选择本轮任务，不一次性全部完成。

推荐顺序不等于强制顺序：

- 用户已经拥有阶段 3 的必要输入并明确要求详细行程时，可以直接进入阶段 3，不强制重新做阶段 1。
- 用户只想整理准备清单时，可以直接进入阶段 2，不要求先生成调研文档。
- 用户要求修改某一既有阶段产物时，只处理该产物，不自动刷新其他阶段。

阶段产物彼此引用但不自动合并。阶段 2 可以根据用户真实进展更新阶段 1 顶部待办，正文候选方案保持不变；任何文件修改仍需用户明确授权。

## 6. 形成确认摘要

正式检索或生成交付前，用一段简短摘要确认本轮范围：

```markdown
我理解本轮是 **阶段 <编号>：<名称>**。

- **已知条件**：<只列会影响结果的信息>
- **暂定假设/待补**：<非阻塞假设；没有则省略>
- **本轮会完成**：<明确交付物和调研范围>
- **本轮不包含**：<相邻阶段或外部动作>

确认后我再开始正式执行。
```

不要把确认摘要写成长问卷，也不要在用户已经明确范围时重新展示完整输入清单。

以下情况视为已经确认，可以直接执行，不再重复请求确认：

- 用户明确回复“确认”“继续”“开始”“按这个做”等同意语句；
- 用户对确认摘要只做局部纠正，并同时表达可以继续；
- 用户先前已经确认本轮范围，随后只是补充所需资料。

以下情况需要重新确认：

- 用户纠正内容改变了旅行阶段、交付物或关键边界；
- 新增请求会把本轮从一个阶段扩大到多个阶段；
- 需要执行此前未说明的文件写入、外部发送、预订或其他有状态操作。

确认授权只覆盖摘要中说明的本轮任务，不自动授权下一阶段或其他外部操作。

- 不默认加载其他阶段文件或案例；只有当前任务真正需要时才读取。

## 路由完成检查

- 阶段由用户当前目的决定，没有仅凭“已订好”或单个关键词误判。
- 已复用现有资料，没有重复询问。
- 阻塞信息和可声明假设已经区分。
- 混合需求已经拆分，没有一次性扩大交付范围。
- 用户知道本轮会得到什么、不会得到什么。
- 用户已经明确确认，且本轮执行没有超出该授权。
- 行后反馈没有被自动写入案例、校准日志或 Skill；任何长期写回都已有明确授权。
