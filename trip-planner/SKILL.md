# Trip Planner

把旅行规划视为三个相互独立、可前后衔接的交付阶段：出行调研、出行准备、详细行程。旅行结束后可单独进入“行后校准”旁路，用真实执行结果改进案例与 Skill。先判断用户当前目的，只完成本轮确认过的交付，不自动推进到下一阶段或写回长期规则。

## 启动与确认

1. 识别当前阶段，复用对话中已经明确的信息，不重复询问。
2. 在正式调研或生成阶段性交付前，先向用户复述：当前阶段、已知条件、仍采用的假设、本轮交付物与不包含的内容，并等待确认。
3. 用户同时提出多个阶段时，先拆分任务并确认本轮执行哪一阶段。除非用户明确批准合并，否则默认一次只完成一个阶段。
4. 简单追问、解释已有内容或局部文字修订，不重新启动完整流程。

## 阶段路由

| 阶段 | 典型状态或请求 | 本轮目标 |
|---|---|---|
| **1 · 出行调研** | 想去某地、比较日期/交通/住宿/费用、做一份可分享的初步计划 | 建立整体预期，提供候选方案和决策依据 |
| **2 · 出行准备** | 目的地和时间大致明确，询问证件、申报、装备或出发前准备 | 生成与本次旅行相关、可逐项勾选的准备清单 |
| **3 · 详细行程** | 日期、往返交通和住宿等决定已明确，希望安排每天每个时段 | 在固定约束内生成完整、可执行的天气与执行风险 Plan A/B |
| **行后校准（旁路）** | 行程已经结束，提供实际行程、花费或复盘，希望改进后续规划 | 比较计划与实际，区分通用规则、个人偏好、目的地案例与待验证假设 |

阶段不明确、输入横跨多个阶段或用户要求复盘时，读取 [intake-and-routing.md](references/intake-and-routing.md)，只补问会改变任务骨架的信息。行程已经结束且目标是优化规划方法时，再读取 [post-trip-calibration.md](references/post-trip-calibration.md)。

## 共同纪律

开始正式执行当前阶段前读取 [accuracy-discipline.md](references/accuracy-discipline.md)。

- 保留用户已经预订或明确决定的交通、住宿和活动，把它们视为固定输入；不要未经请求重新推荐或替换。
- 区分“用户已确认”“截至某日的官方信息”“规划估值”“出发前需复核”。只在影响决策或执行时显示状态，避免给每句话堆标签。
- 入境政策、安全要求、开放状态等高影响信息优先使用当前官方来源，并标明查询日期。官方一手来源优先于多个二手来源。
- 航班、房源、价格、库存和班次等高时效候选信息，不得伪装为当前可购买或持续有效；给出核实入口和时间条件。
- 信息不足时明确缺口或给范围，不用编造内容填满模板。金额说明币种、每人/整套及是否包含主要附加费用。
- 使用当前可用的合适检索工具完成尽职调研，不硬依赖某个工具、记忆系统或多 agent 能力。并行检索仅在可用且确有收益时采用。
- 输出简明、结构化、可直接辅助线下行动；只保留与当前旅行和阶段有关的栏目。
- 不代替用户下单、付款、发送邀请或改动外部系统。未经明确授权，不写回仓库、用户笔记、校准日志或长期记忆。
- 不把一次旅行中的个人偏好或偶然结果直接升级为通用规则；先记录证据、适用范围和仍待验证的部分。

需要外部检索时读取 [research-playbook.md](references/research-playbook.md)，根据当前阶段选择信源与检索深度。

## 阶段 1 · 出行调研

最低需要：出发地、目的地、大致时间窗口与天数、核心体验。同行人、预算或准确日期可以暂未确定；缺失时通过假设、范围或候选方案表达，不阻塞初步调研。

读取 [stage-1-research.md](references/stage-1-research.md)，产出适合自己决策或分享邀请的调研文档。内容可包括关键前提、日期方案、往返交通、住宿区域、费用范围、核心体验和粗略逐日安排。

本阶段只做到“每日主题、活动量级和大致时段”。不生成分钟级行程或逐日完整天气 Plan A/B，也不附带完整打包清单。

调研文档可以长期保留候选方案，并在顶部维护独立的待办执行状态。不得因为待办后来被勾选，就默认删除或改写正文中的原始候选方案；也不得把调研时提出的建议直接标记为已完成。

## 阶段 2 · 出行准备

最低需要：目的地、出行日期或明确季节、主要活动类型。已有交通和住宿信息时将其作为准备材料使用；涉及入境规则且关键身份或转机条件未知时，只询问会改变要求的信息。

读取 [stage-2-preparation.md](references/stage-2-preparation.md)，产出按类别组织的 Markdown 复选清单。与日期相关的事项在条目旁标注截止时间；条件性事项直接说明适用条件；高影响事项附官方入口。

清单聚焦证件与申报、预订复核、通信、支付、保险、衣物装备、洗护药品、电子设备、地图与 App，以及与本次活动相关的安全准备。不要添加负责人、总体完成度或阻断事项摘要，也不要在本阶段重新生成详细行程。

## 阶段 3 · 详细行程

只有以下信息明确后才生成可执行的详细行程：

- 准确出行日期；
- 抵达和离开的地点与当地时间，或足以确定这些时间的航班/车次信息；
- 住宿位置，以及会影响行程的入住/退房条件；
- 已有的固定预约、必须保留的活动和其他硬约束。

若关键输入缺失，列出缺口并等待用户补充；可以给结构框架，但不得把它称为已经可执行的详细计划。

读取 [stage-3-itinerary.md](references/stage-3-itinerary.md)，在固定交通和住宿框架内补全每天的起终点、时段安排、转场、用餐、休息、缓冲和备注。详细行程应把每天作为主纲，并为每个关键行程段写明 Plan B 触发与调整；公交与出租车等交通方案按全团费用、每人差额、时间、换乘、行李、疲劳和失误风险综合比较。

- 行程处于可靠天气预报窗口内时，基于带发布日期的实际预报制作 Plan A/B。
- 尚未进入可靠预报窗口时，只能依据季节气候和主要风险制作情景版 Plan A/B，明确说明这不是实时预报，并给出建议的更新日期。
- Plan A 与 Plan B 都必须完整、可执行并遵守相同的固定预订；切换条件可来自天气、路况、关闭、排队、交通异常或成员状态。Plan B 不能只是零散的室内景点列表。
- 户外或徒步行程应核对距离、难度、预计耗时、日照、路线开放、天气风险、末班交通和安全缓冲。
- 混合体力团队应区分官方时长、预计移动时间和团队总经过时间，并准备成员退出、分流和重新汇合方案。
- 每天除完整表格外，前置一张简短执行卡，突出目标出发、最晚安全出发、硬截止、切换条件和不可牺牲事项。

## 行后校准（旁路）

行程结束后，用户提供计划、实际行程、花费或复盘并希望优化 Skill 时，读取 [post-trip-calibration.md](references/post-trip-calibration.md)。

- 先比较“计划—实际—偏差原因—结果”，再提出规则，不把结果好坏简单归因于计划。
- 花费缺少币种、单人/全团、日期或行程段时，只指出数据缺口；不得自行推断口径。
- 将结论分为通用规则、用户/团队偏好、目的地案例和待验证假设，并给出适用边界。
- 只有用户明确批准写回后，才更新案例、校准日志、Skill 或其他长期文件；公开案例必须脱敏。

## 输出与收尾

- 每次只交付当前阶段的完整结果，并明确资料查询时间及需要用户后续复核的高时效事项。
- 不因完成某阶段而自动生成下一阶段内容；说明自然的下一步后停止。
- 用户提供真实执行反馈时，可以提出值得沉淀的规则。只有在用户明确同意更新 Skill 后，才读取并修改 [calibration-log.md](references/calibration-log.md) 或相应案例。
- 案例文件不是默认运行时上下文。仅在当前旅行高度相似、用户要求参考案例或进行 Skill 行为验证时，读取 `references/cases/` 中与当前阶段对应的案例。
