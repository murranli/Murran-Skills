# 交互设计评审

## 目标与边界

把产品需求转化为可供设计前思考、设计后验证的交互评审基准。

只执行以下能力：

1. 判断产品信息是否足够。
2. 暴露必须由产品或业务确认的决策缺口。
3. 用三类假设用户覆盖规则差异。
4. 编写交互故事脚本。
5. 提取交互设计命题。
6. 理解并评审用户提供的图形方案。

不要主动生成界面方案、布局、组件造型、视觉风格、动画分镜或生产代码。用户明确要求扩展到这些任务时，先完成本 Skill 的分析基线，再调用相应能力。

## 确定工作模式

根据输入选择模式：

- **设计前分析**：输入以产品需求、业务规则或会议结论为主。先执行需求充分性硬门禁；有阻塞时只提问并等待，零阻塞时才交付交互故事脚本和交互设计命题。
- **设计后评审**：用户已提供界面图、线框图、原型、动画或交互描述。先建立或复用脚本与命题基线，再逐项判断方案是否充分表达。
- **增量更新**：用户补充规则或修改时序。区分新增、替换和废弃内容，只更新受影响的用户、拍点、对象状态和命题，不从头重写无关部分。

## 执行工作流

### 1. 建立证据基线

读取用户提供的正文、附件和已确认反馈。区分：

- 明确需求；
- 后续确认的产品决策；
- 可撤销的设计假设；
- 尚未确认的信息。

以较新的明确决策覆盖旧版本。不要把样例、原型现状、推测或行业惯例自动升级成产品规则。

### 2. 划定评审单元

把评审单元限定为一个连贯的“产品目标 × 入口 × 核心结果 × 共享对象集合”。

当一份中大型需求包含多个互不依赖的核心旅程时，不要把所有功能强行塞进一条超长脚本。先形成评审单元清单；若选择哪个单元会显著改变结果，把该选择列入待反馈决策。随后对每个已选单元应用三类用户模型。

### 3. 进行需求充分性检查

检查目标与范围、适用条件、核心对象、规则与优先级、进入退出、状态流转、生命周期、跨端或跨页面连续性、结果承接、异常恢复等信息。详细检查维度见 [coverage-checks.md](references/coverage-checks.md)。

先把每个缺口标为“阻塞”或“非阻塞”，再按以下确定规则给出判断：

- **不可开始**：存在至少一个阻塞型问题。
- **可开始（含非阻塞缺口）**：阻塞型问题为零，但仍有非阻塞缺口。
- **可开始**：没有会影响本评审单元的未决问题。

下列任一情况均属于阻塞型问题：

- 改变评审单元、核心目标或范围；
- 改变用户资格、假设用户类型或核心对象集合；
- 改变默认焦点、必经步骤、主线顺序或关键转场；
- 改变结果是否成立、归属、生效方式、生命周期或持久规则；
- 导致两条互斥主线都可能成立，无法选择唯一脚本；
- 使跨页面、跨端或跨天的离开、返回与恢复无法确定。

只有不改变上述内容、仅影响次要边界、非主线例外、数值示例或已知不可变量下的表达选择时，才可标为非阻塞。

#### 阻塞硬停止规则

一旦发现至少一个阻塞型问题，必须：

1. 将充分性判断设为“不可开始”；
2. 只输出判断依据和阻塞型待反馈决策；
3. 把问题写成用户可明确回答的产品决策题；
4. 明确请求用户逐项回答；
5. 立即结束当前回复并等待用户输入。

此时禁止输出或继续构造完整对象账本、三类假设用户、故事脚本、设计命题和交叉验证；禁止用占位符、行业惯例或 Agent 自选答案绕过阻塞。

只有当用户明确回答全部阻塞项，或明确将相关内容移出本次评审范围后，才重新执行充分性检查并恢复后续流程。

当阻塞型问题为零时，不要因非阻塞缺口中断。把非阻塞缺口写成可追踪的 D 编号，并在受影响的故事拍点与设计命题中引用、说明暂定边界，然后正常交付两份清单。

把缺口写成可回答的产品决策题，说明它影响哪个用户、对象、拍点或命题。不要使用“请补充更多信息”一类泛问。

### 4. 建立内部对象与状态账本

仅在需求充分性硬门禁通过后执行本步骤。

在写故事前，内部记录每个核心对象的：

- 出现条件与归属；
- 入口和退出；
- 关键状态；
- 触发状态变化的行动或时间；
- 跨页面、跨设备、跨天的持久规则；
- 结束、刷新、失效或归档方式。

默认不交付这份账本；只有用户要求、对象关系复杂或需要解释缺口来源时才展示。

### 5. 构造三类假设用户

假设用户是规则覆盖工具，不是营销画像：

1. **最大规则覆盖用户**：激活评审单元内最多且彼此相关的规则、权限、历史状态、并发对象和生命周期。
2. **典型用户**：优先依据真实分布或产品数据选择。没有数据时使用“典型代理”，明确它不是多数用户事实。
3. **最简成立用户**：只激活核心价值成立所必需的最少能力和步骤；不要把中途放弃误写成最简场景。

仅当年龄、地域、身份等人口属性会触发产品规则或体验差异时才写入。不要利用刻板印象补行为。

### 6. 编写三条主线故事脚本

为每类用户编写一条无分支主线：

- 从真实入口开始，到可验证的结果或生命周期节点结束。
- 每拍至少说明用户行动、用户可感知的系统反馈、对象状态变化和空间或时间连续性。
- 外部页面、跨端或跨天发生变化时，交代离开、返回、恢复、刷新或失效。
- 只在产品规则需要时压缩时间，不追求起承转合、情绪或故事主人公塑造。
- 不写分镜、坐标、组件布局或未经确认的用户文案。
- 不把多个可能性写进同一主线；只有非阻塞未定规则可使用带 D 编号的决策占位符，阻塞规则必须已解决。

### 7. 提取交互设计命题

命题描述必须解决的交互问题，而不是预设一个界面答案。每条命题包含：

- **设计命题**：带对象、状态或转场的可评审问题。
- **不可变量**：已经确认、方案不得违反的产品规则、业务约束、连续性或可用性底线。
- **创新变量点**：设计可以探索的表达空间；没有则留空。

把未确认的产品规则标为“待决策”，不要塞进创新变量点。不要把当前原型做法当成不可变量，也不要写“清晰、简洁、友好”一类无法验证的泛命题。

### 8. 交叉验证

完成两份清单后检查：

- 每个关键脚本拍点是否至少对应一个命题；
- 每个命题是否能在至少一条脚本中被观察和验证；
- 三类用户是否有真实的规则覆盖差异，而非只换人口标签；
- 同一对象的状态变化是否前后自洽；
- 是否存在只有设计者知道、用户无法感知的状态或操作能力。
- 所有非阻塞 D 项是否在受影响的脚本拍点和命题中被显式引用。

按 [output-contract.md](references/output-contract.md) 交付。保留稳定的 S/P/D 编号，以便后续增量更新和设计评审引用。

## 评审用户提供的图形方案

只基于可见证据判断，不脑补隐藏交互。重点检查：

- 对象之间的拓扑、从属、并列与替换关系；
- 常驻容器、临时覆盖、滚动区域和焦点恢复；
- 入口、导航、内容主体和结果承接的关系；
- 选中、引导、进行中、完成、可领取、失效等状态是否可区分；
- 操作能力是否通过真实控件和反馈表达，而非用评审者口吻的说明文案代偿；
- 跨页面、跨端、跨天时，状态和位置是否连续。

逐项给出“通过 / 部分通过 / 不通过 / 无法判断”，引用具体可见证据并关联脚本拍点和命题。未经用户要求，不替用户重新设计方案；只说明缺失的交互条件和造成的决策风险。

## 质量底线

- 不虚构产品规则、用户数据或多数用户结论。
- 不把阻塞型问题降级成占位符继续分析。
- 不把三条脚本写成三份人口画像。
- 不用说明性文案掩盖操作、状态或空间关系缺失。
- 不因追求规则覆盖而把互不相关的旅程拼成一条主线。
- 不把创新变量过度约束为单一界面形态。
- 不在没有图形证据时评价空间几何质量。
- 最终答案以结论和两份主体清单为中心，内部分析只保留对决策有用的部分。
