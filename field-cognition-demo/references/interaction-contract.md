# `/需求识别` 前台交互契约

## 目标

让设计师在当前画板旁用不到一分钟理解并校准一条规则链。前台只呈现支持当前设计判断的信息，后台技术结构延后展示。

## 识别阶段

1. 解析客户端提供的文件、需求、已选画板和画板可见内容。
2. 按 `demo-knowledge.md` 的命中规则选择一条规则链。
3. 如果没有已选画板，也没有命令参数，只提示用户先选择一个画板并重新输入 `/需求识别`；不要假装读取成功。
4. 如果没有命中演示知识，说明未命中，并列出已读取到的上下文，不生成候选规则。

## 规则链卡格式

保持简洁，可使用以下结构，但不要为了形式重复信息：

```markdown
### 需求识别 · 1 条相关规则链

**当前画板**　{真实画板名或“未提供”}  
**规则链**　{规则链标题}  
**状态**　局部需求认知 · 未确认上线

**目前材料支持**

{3 至 5 步因果链；未知位置直接写“未知”}

**为什么影响当前设计**

{一句具体设计影响}

**本次只确认一个问题**

> {唯一高优问题}

可以直接说明你的判断；如果不确定，告诉我建议找谁确认即可。
```

不要显示主张 ID、JSON、置信度小数、数据库字段或完整证据清单。

## 处理用户回答

### 可直接形成候选主张

当回答明确说明对象、条件和结果时，将其拆成彼此独立的原子主张。例如：

```text
“取消主品后子品不能结算，但重新勾选会重新算换购价”
```

拆成：

- 主品取消勾选后，子品结算资格失效；
- 主品重新勾选后，子品换购价重新计算。

两条都只能标记为 `local-candidate`，适用范围默认是当前需求或当前画板。

### 保留未知

- 用户明确不知道：不更新主张，记录建议确认对象。
- 回答只覆盖价格或结算其中之一：只更新被明确回答的一项，另一项保持未知。
- 回答含糊到无法判断“失效”指什么：只追问一次具体指代；仍不清楚则保留未知。
- 回答与材料冲突：保留双方内容，标记 `conflicted`，不要选边覆盖。

### 推断边界

如果为了拆分而进行了语义归纳，在事件的 `inference_notes` 中说明。不能把系统推断写成用户原话。

## 校准回执

完成后显示：

```markdown
### 已记录 · CAL-0001

- **当前范围：** 仅当前需求/画板
- **本次变化：** {新增或修正了什么；没有则写“未修改主张”}
- **仍待确认：** {保留的关键未知}
- **模型影响：** 局部候选认知，未晋升为场域规则
- **记录状态：** 会话级演示，未写入正式后台

输入 `/后台记录` 可查看原始回答、主张拆分和前后差异。
```

随后按 `SKILL.md` 追加隐藏事件注释。前台回执不要暴露隐藏 JSON。
